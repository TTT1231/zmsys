# BOM 卡顿现场取证指引

背景：本机受控环境（生产构建 + 真实后端 + 1x 档数据 ≈ 生产量级）未复现"加载卡顿"，
已测成本均低于可感知口径（见 out/bom-perf-audit-updated.md §1/§6）。定位真实卡顿需要
在实际使用的设备与网络上采集一次现场证据，步骤如下（5 分钟内完成）。

## 一、出现卡顿时（不要刷新页面）

1. 按 `F12` 打开 DevTools，切到 **Performance（性能）** 面板。
2. 点左上角 **录制（●）**，把刚才卡顿的操作**原样再做一次**（如：打开 BOM 页 / 搜索 / 切筛选）。
3. 点 **停止**，得到时间轴。
4. 保存：右键时间轴 → **Save Profile…**，存为 `.json` 文件（比截图有用得多）。
5. 顺手记录：当时在哪个页面、点了什么、大概卡了几秒。

## 二、网络侧（同一次 F12 会话）

1. 切到 **Network（网络）** 面板，勾选 **Disable cache**，刷新页面。
2. 等页面完全加载后，把左上角摘要（总请求数 / 总传输量 / DOMContentLoaded / Load 时间）
   截图；如有红色失败请求一并截。
3. 若怀疑是某个接口慢：点该请求 → **Timing** 标签页截图（区分排队/TTFB/下载）。

## 三、把材料交给分析

- DevTools Profile 的 `.json` + 截图 + 一句话场景描述即可。
- 分析端可用仓库内链路复跑对照：`node out/perf-lab/run-sweep.mjs --checkpoint <label> --out out/perf-lab/v2/e2e-<label>.json`
  （口径见报告 §5.2；Event Timing/trace 采集器已就绪）。

## 四、先验线索（来自生产 op_log，2026-09-16→09-29，177 条写操作）

- 团队 3 人：梁静（super，建单/归档/删单 93 次）、吉英（warehouse，发货/入库 67 次）、郭均（super 16 次）。
- 高频写路径 = 建单(46) → 发货(41) → 入库(29) → 批量归档(22)；均触发快照失效与订单/入库页重渲染
  ——P2 已把该路径派生成本从 O(N²) 降为一次 O(N·logN)。
- 曾出现 3 分钟内连续 21 次归档（2026-09-27）：连续 mutation→刷新循环是"操作后整页发沉"的候选体感来源。
- **op_log 只记写操作**：纯浏览/搜索/筛选的卡顿不留痕，只能靠上面第一、二节的现场采集。
