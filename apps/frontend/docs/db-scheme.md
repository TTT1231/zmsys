# 数据库表结构设计文档

## 0. 全局约定

- **主键 id**：bigint，**已确定由应用层雪花算法（Snowflake）生成**——并发安全、趋势递增、不暴露业务规模。（表结构与 AUTO_INCREMENT 自增完全相同，仅号的来源不同。）
- **外键**：一律指向被关联表的**主键 id**，不指向业务编码。
- **业务编码**（customer_code / bom_code / order_no / no）：仅供人阅读与检索，不参与表关联。
- **API / 前端对接**：接口与页面一律使用业务编码（order_no / customer_code / bom_code / 单号 no / 用户账号 account），**不传输、不使用雪花 id**；用户操作（启停、编辑）以 account 定位。
- **账号不可改**：sys_user.account 创建后不允许修改（name 可改），需要变更账号时停用重建——account 是前端定位用户的唯一键。
- 保险措施：若个别接口确需回传 id，后端将 Long 序列化为字符串（64 位雪花超出 JS Number 安全整数范围，直接发数字会被 JSON.parse 静默截断成错值）。
- **派生字段不落库**（API 返回时实时计算，勿建冗余列）：
    - 订单累计已发 `outbound` = 该订单出库台账 Σqty；
    - 可用库存 = 该 BOM（Σ入库 − Σ出库），无独立库存表；
    - BOM 规格摘要 `spec`（列表/搜索用）= 从 JSON 规格派生，口径：型号 + 逐项「键 值」（跳过空值与品类常量项），与前端 `src/data/views.ts` 同源逻辑；
    - 客户合作状态（合作中/待跟进）= 聚合查询（口径见待办）。
- **时间字段返回约定**：datetime 字段按 API 契约拆为 `date`（yyyy-MM-dd）+ `time`（HH:mm）两个字段返回，本地时区。

### 0.1 单号/编码生成规则

| 编码                   | 格式                                                   | 序号口径                                                                                   | 溢出                           |
| :--------------------- | :----------------------------------------------------- | :----------------------------------------------------------------------------------------- | :----------------------------- |
| 订单号 order_no        | `ZM` + yyMMdd + **3 位序号**（如 ZM260910001）         | **按日递增**，每日从 001 重置；单号中的日期取订单的 order_date（补录历史单据时即历史日期） | 内网单量按日不会满 999，不处理 |
| 入库单号 no            | `RK-` + yyyyMMdd + **4 位序号**（如 RK-20260910-0001） | 按日递增，每日从 0001 起                                                                   | 同上，不处理                   |
| 出库单号 no            | `CK-` + yyyyMMdd + **4 位序号**（如 CK-20260910-0001） | 按日递增，每日从 0001 起                                                                   | 同上，不处理                   |
| 客户编码 customer_code | `CUS-` + **4 位序号**（如 CUS-1024）                   | 全局递增，不重置                                                                           | 同上，不处理                   |

> **并发取号**：「查当日最大序号 + 1」在并发下可能撞号，靠各编码列的**唯一索引**兜底（插入冲突即重试取号）。内网低并发无需独立发号器。
> **解析注意**：解析序号一律取「前缀 + 日期段之后的全部数字」，禁用 `slice(-N)` 定宽截取。

## 1. 基础业务表

### 1.1 客户表 (custom_table)

| 字段名         | 数据类型 | 说明/备注                                                            |
| :------------- | :------- | :------------------------------------------------------------------- |
| id             | bigint   | 主键                                                                 |
| customer_code  | varchar  | 客户编码 (唯一，`CUS-` + 4 位序号，如 CUS-1024，服务端生成)          |
| name           | varchar  | 客户名称                                                             |
| contact_person | varchar  | 联系人                                                               |
| contact_phone  | varchar  | 联系人电话（存完整号；API 一律只返回掩码如 138****6821，不出完整号） |
| province       | varchar  | 省/直辖市（行政区划四级之一，前端级联选择）                          |
| city           | varchar  | 市（直辖市为「市辖区」级）                                           |
| district       | varchar  | 县/区（可空——东莞等直筒子市无区级）                                  |
| town           | varchar  | 乡镇/街道（可空）                                                    |
| address        | varchar  | 详细地址（如「示例街道 88 号」，跟在四级行政区划之后）               |
| owner_id       | bigint   | 所属销售 (外键 → sys_user.id，role=sales 的用户；建档时指定，可改)   |
| pay_terms      | varchar  | 付款条件（建档可填，可编辑，如「月结 30 天」）                       |
| created_at     | datetime | 审计时间                                                             |
| updated_at     | datetime | 审计时间                                                             |

> **备注**：
>
> - 合作状态（合作中/待跟进）不存字段，聚合派生：**近 6 个月内有订单 = 合作中，否则待跟进**（窗口可调；新建客户尚无订单即为待跟进）。
> - 客户档案可编辑（联系人/电话/行政区划/详细地址/付款条件/所属销售），不可删除。
> - 行政区划数据源：前端 `china-division` 数据集（省→市→县区→乡镇四级级联），后端不校验区划合法性，仅存储。

### 1.2 销售订单表 (sales_order_table)

| 字段名             | 数据类型 | 说明/备注                                                       |
| :----------------- | :------- | :-------------------------------------------------------------- |
| id                 | bigint   | 主键                                                            |
| order_no           | varchar  | 订单号 (唯一，`ZM`+yymmdd+3 位序号，如 ZM260903086，服务端生成) |
| customer_id        | bigint   | 客户ID (外键)                                                   |
| bom_id             | bigint   | 对应的bom (外键)                                                |
| qty                | int      | 订单数量                                                        |
| order_date         | date     | 下单日期                                                        |
| deliver_start_date | date     | 交货起始日期                                                    |
| deliver_end_date   | date     | 交货截止日期（排序/逾期口径）                                   |
| remark             | text     | 订单备注                                                        |
| created_at         | datetime | 审计时间                                                        |
| updated_at         | datetime | 审计时间                                                        |

> **备注**：
>
> - 累计已发数量（outbound）不落库，由出库台账按订单聚合（见 §0 派生字段）。
> - 新建订单表单的交期为起止区间，起止日期均落库；交期排序、逾期判断、库存预留优先级统一按**交货截止日期**计算（与前端 `src/data/views.ts` 同口径）。
> - **订单不可删除**；修改数量时**新数量必须 ≥ 累计已发数量**（低于已发即 400 拒绝——订单 1000 件已发 800 时最多改到 800，不能改小到 500 规避超发事实）。
> - 创建时校验：customer_code / bom_code 必须存在；交货截止日期不得早于起始日期。

### 1.3 产品/BOM表 (bom_table)

| 字段名     | 数据类型 | 说明/备注                                                      |
| :--------- | :------- | :------------------------------------------------------------- |
| id         | bigint   | 主键                                                           |
| bom_code   | varchar  | 编码（唯一，`ZM+品类码+序号`，如 ZMXK2001/ZMXK3001/ZMKW0001）  |
| name       | varchar  | 品类（旋转开关 / XK3 / 新微动 / 老微动 / 琴键开关…，按需扩充） |
| model_code | varchar  | 型号（各品类通用语义，如 2-1、XK3、KW-1、KW16、KQ-1）          |
| spec       | JSON     | 品类专属规格键值对，只存该品类用到的键，示例见下               |
| unit       | varchar  | 单位（个）                                                     |
| created_at | datetime | 审计时间                                                       |
| updated_at | datetime | 审计时间                                                       |

> **设计说明**：
>
> - 不同品类的规格维度不同（旋转开关有脚位/档位，微动类有按钮高度/镀层），固定列会导致稀疏宽表且每加品类都要改表结构，故用 JSON 按品类存键值，加新品类零 DDL。
> - 品类模板（各品类有哪些规格键、下拉选项）由前端常量维护（`src/data/categories.ts`），不落库；后端仅校验品类存在（模板中的必填项仅作前端表单引导，不作服务端强校验，允许自由规格）。
> - 编码前缀映射（系列号入品类码，序号宽度随品类）：旋转开关 XK2（ZMXK2001 起，3 位）、XK3 XK3（ZMXK3001 起，3 位）、新微动 KW（ZMKW0001 起，**4 位**）、老微动 KW16（ZMKW16001 起，3 位）、琴键开关 KQ（ZMKQ001 起，3 位）；序号在各品类内独立自增。
> - 规格摘要（API 的 `spec` 字符串）由服务端从 JSON 派生返回，不落库（口径见 §0 派生字段）。
> - 需要按某个规格属性检索时，用 MySQL 8 虚拟列 + 索引按需提取，例如：
>   `ALTER TABLE bom_table ADD COLUMN foot VARCHAR(16) GENERATED ALWAYS AS (spec->>'$.脚位') VIRTUAL, ADD INDEX idx_foot (foot);`

`spec` JSON 示例：

### 1.5 出库流水表 (outbound_ledger)

| 字段名      | 数据类型 | 说明/备注                                |
| :---------- | :------- | :--------------------------------------- |
| id          | bigint   | 主键                                     |
| no          | varchar  | 出库单号 (唯一)                          |
| order_id    | bigint   | 订单 (外键 → sales_order_table.id)       |
| qty         | int      | 本次出库数量                             |
| out_date    | datetime | 出库时间                                 |
| operator_id | bigint   | 操作人 (外键 → sys_user.id，显示时 join) |
| remark      | varchar  | 备注                                     |
| created_at  | datetime | 审计时间                                 |
| updated_at  | datetime | 审计时间 (支持更正记录)                  |

> **出库可发量校验（必须实现，与前端同口径）**：
> 同一 BOM 的可用库存在**全部未完成订单间共享**（不按订单隔离）。校验某订单本次发货量时：
>
> 1. 取该 BOM 当前可用库存（Σ入库 − Σ出库）；
> 2. 将该 BOM 的未完成订单按**交期升序、同交期按单号**排序，从库存池逐单分配预留（每单最多预留其剩余待发量），排在前面的订单优先占用库存；
> 3. 目标订单分到的预留量即本次最多可发量，**超出即拒绝**（400：可发库存已变化，请重新核对数量）。
>
> ⚠️ 不能简化为「qty ≤ 该 BOM 总库存」——那会超卖交期更早的订单。前端展示口径见 `src/data/views.ts` 的 `readyToShip`/`maxShipOf`，两边必须一致。
>
> **事务性**：可发量计算与出库落库必须在同一事务内完成（对台账聚合加锁或使用行锁），防止并发请求双双通过校验导致超卖。

### 2.4 操作日志表 (op_log)

| 字段名      | 数据类型 | 说明/备注                                                                                    |
| :---------- | :------- | :------------------------------------------------------------------------------------------- |

## 💡 关联关系推断说明 (基于外键)

- `sales_order_table` 关联 `custom_table` (多对一，customer_id → 客户表 id) 和 `bom_table` (多对一)。
- `custom_table` 的 `owner_id` 关联 `sys_user` (多对一，所属销售)。
- `inbound_ledger` 关联 `bom_table` (多对一)。
- `outbound_ledger` 的 `order_id` 关联 `sales_order_table` (多对一)；客户与 BOM 信息经订单间接取得。
- `inbound_ledger` / `outbound_ledger` 的 `operator_id` 关联 `sys_user` (多对一，显示操作人姓名时 join)。
